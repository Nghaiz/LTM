## 1. Summary

The implementation and the 600-second soak are complete. The status remains partial only because
the frozen protocol has no safe NAT-rebind token and the zero-allocation target needs profiling.

Phase 02 adds endpoint-keyed multi-connection routing, a 16-player-capable server, congestion
hysteresis, a 64-packet reliable sliding-window guard, bounded IP rate limiting, challenge-table
eviction, unknown/bad-connection counters, and a hand-rolled benchmark. The localhost runs proved
16 simultaneous connections and 30 Hz traffic, including the recorded 600-second soak.

## 3. Benchmark result

Commands: `dotnet run --project Ironfront.Net.Transport.Bench -c Release -- --connections 16 --seconds 10` and
`dotnet run --project Ironfront.Net.Transport.Bench -c Release -- --connections 64 --seconds 20`.

Observed output: header parse 6.2 ns/op, reliability receive 2.9 ns/op, pool 100k rent/return
1.2 ms with zero growth. The warmed 16-connection run delivered 4,848 messages in 10 seconds at
2.97% CPU; its send and poll regions measured zero allocation. The 64-connection run delivered
38,784 messages in 20 seconds at 0.39% CPU and remained connected.

## 4. Technical decisions

| Problem | Chosen | Reason |
|---|---|---|
| Endpoint routing | IPv4 value key | Avoids per-packet endpoint hashing/allocation |
| Congestion response | Two modes with 200/250 ms hysteresis and 10 s dwell | Stable, explainable, within frozen spec |
| Receiver pressure | 64 unacked reliable cap plus advertised pressure | Bounded memory and simple sliding-window behavior |
| Pre-auth flood | 5 requests/IP/s, 10k entry cap, oldest-half eviction | Prevents both request flood and limiter-table exhaustion |

## 5. Security/impact

Resource creation is bounded before authentication: pending challenges are capped, rate-limited,
and cleaned; fragment groups and reliable windows are bounded. Bad protocol IDs are dropped by the
shared parser and unknown connection IDs are silent drops. Changes are confined to Dev B transport,
its test project, benchmark and reports; no gameplay or shared wire format was modified.

## 6. Pending verification

The earlier 600-second run proved connection stability: 16/16 connections, 290,912 messages and
no disconnect observed. The final warmed 16-connection run measured 2.97% CPU with zero bytes in
the steady send/poll regions; the final 64-connection run measured 0.39% CPU and held 64/64
connections for 20 seconds. The benchmark's total thread allocation includes harness work outside
those regions and is reported separately from the transport hot path.

The .NET 8 target uses the allocation-free `SocketAddress` receive/send overloads and caches
serialized IPv4 destinations. The Unity-compatible netstandard2.1 target retains the managed
EndPoint fallback because those overloads are not in its reference surface; this remains an
explicit platform limitation for the zero-allocation criterion and needs a Unity-side profiler
before it can be claimed there.

The phase-02 NAT-rebind sketch requires a `RebindToken`, but the frozen GSP header and handshake
messages define no such field. The transport does not silently invent a wire extension; this needs
a protocol-owner decision before implementation, otherwise an endpoint change remains rejected.
