2. WHAT ACTUALLY STOPS THE KILL
-------------------------------

Everything upstream of the hit test is now correct, and the artifact says so rather than
assuming it:

    present.torso == frame.torso to seven significant digits   (X-19 stays closed)
    frame.tick == wanted.tick on every line                    (the right pose was rewound to)
    aim.resolved = true, targetActorId = 42, distanceM = 4.65  (the solver found the victim)
    target inSnapshot = true, proxy == snapshot to the centimetre
    occluded = 0                                               (nothing in the way)

A shot that resolves, at 4.7 m, against a live target whose pose the server and client agree
on, with no wall in between, and it does not hit. From the logged line:

    origin  = 1906.5, 27.5, 1798.6      aim = -0.38, -0.01, -0.92
    torso   = 1904.594, 27.084, 1794.257   extents = 0.25, 0.35, 0.16

`HitboxSet.FromSize` builds four boxes off the feet (centre, full size):

    legs    0.45   0.90 tall     ->  0.000 .. 0.900
    torso   1.20   0.70 tall     ->  0.850 .. 1.550
    arms    1.25   0.60 tall     ->  0.950 .. 1.550
    head    1.70   0.24 tall     ->  1.580 .. 1.820

Torso and arms both stop at 1.550. The head starts at 1.580. **Nothing covers 1.550 .. 1.580 --
a 3 cm horizontal seam across a standing body.** A ray through it hits no box and returns Miss
before the occlusion test is ever reached, which is why `occluded` stays 0.

The logged ray arrives at the target 1.5684 m above its feet. That is inside the seam: 0.0184 m
above the torso, 0.0116 m below the head.

WHY IT LANDS THERE, AND WHY EVERY SHOT DOES. `ScriptedTargetSolver` raises BOTH endpoints by
`ScriptedAim.DefaultAimHeight` = `ProtocolConstants.EYE_HEIGHT` = 1.6, and its remark explains
the intent -- aiming at the target's origin from 1.6 m up would be a downward shot into the
feet. But feet + 1.6 is not centre of mass, it is 0.02 m inside the head box's lower edge. On
level ground the shot leaves at 1.6 and arrives at 1.6, and the whole margin between a headshot
and nothing is two centimetres. This is not a close-range artefact: both endpoints move
together, so the aim point is 1.6 m at every range.

CONFIDENCE, STATED HONESTLY. The seam is a fact of the source and needs no run to confirm. The
claim that THIS ray threaded it is arithmetic over a log line whose `aim` is rounded to two
decimals, and +/-0.005 on the y component is +/-0.024 m at 4.74 m -- wider than the seam itself.
So read section 2 as: the ray arrives at 1.568 +/- 0.024, a band that runs from just inside the
torso to just inside the head, and the seam sits in the middle of it. Consistent, not proven.

THE NEXT MEASUREMENT, and it is one line. `LagCompensator.Resolve` already loops all four boxes
per target; on a miss, record the nearest box and its signed miss distance instead of discarding
them -- the same move 3F.1 made for X-19 and this commit made for occlusion. That turns
"consistent with the seam" into "the ray missed head by 0.0116 and torso by 0.0184", or names
something else entirely. Do not fix the seam before that line exists: a fix with no failing
measurement in front of it is a guess with a commit message.

5. THE BUILD THIS RUN NEEDED FIRST
-----------------------------------

The player could not be built at all. `com.ivanmurzak.unity.mcp` 0.90.0 and its ten extension
packages (#175) installed McpPlugin.dll and McpPlugin.Common.dll with `defineConstraints: []`
while every other DLL of the same closure -- R3, ReflectorNet, SignalR, Microsoft.CodeAnalysis
-- carried `- UNITY_EDITOR`. McpPlugin.dll references R3, so the player included the first,
excluded the second, and UnityLinker died with

    Mono.Cecil.AssemblyResolutionException: Failed to resolve assembly: 'R3'

naming R3, the file that was correct, and never naming McpPlugin.dll, the file that was wrong.

Two .meta lines fixed it and the build succeeded on the retry -- which is the whole causal
proof: same tree, same command, one constraint added, Failure -> Success.

It was never only a compile problem, and the reach beyond the harness is DERIVED rather than run.
No Linux dedicated-server build was attempted for this report. What is measured is that the
Windows player's linker input listed McpPlugin.dll and McpPlugin.Common.dll among its allowed
assemblies and did not list R3. What follows from the source, and not from a run: defineConstraints
are evaluated against the target's define set, UNITY_EDITOR is false in every player of every
target, and these .meta files carry no Server-specific platform entry (`Any: enabled: 1`, and only
WindowsStoreApps disabled). So the server build takes the same two DLLs into the same linker and
should fail the same way -- and a build that HAD linked would have carried an HTTP bridge hosting
Roslyn into the game server image, the exact thing `EditorBuild.StripEditorOnlyDefines` was written
to prevent. Read that as: the mechanism is shared, the failure is expected, nobody has watched it.
Cheap to settle whenever a release build is next made; not worth a Linux toolchain run today,
because the fix is identical either way.

Nothing in CI could see it: no job builds a Unity player, `images.yml` downloads a pre-built
Linux artifact from a release, and `build-test` is `dotnet build` over the pure-.NET libraries,
which never reads Assets/Plugins. Four days, unnoticed. And because the .meta files are
generated by the MCP package's own NuGet installer, the next upgrade would have silently undone
the hand-fix.

So the fix ships with `tools/check-plugin-define-constraints.ps1`, wired into ci.yml as a HARD
gate. It reads the bridge's package list from `.nuget-installed.json` rather than hardcoding DLL
names, so a fourth bridge DLL is covered the day it lands.

Mutation-proved, one fault, one mutant, one red: reverting McpPlugin.dll.meta to
`defineConstraints: []` turns the gate red naming that exact file; restoring it turns it green.

A first version of that gate is worth recording because it was WRONG in an instructive way. It
walked assembly references and failed any player-included plugin referencing an editor-only one
-- and reported 22 violations against a tree whose player build succeeds. The BCL shims in that
folder (System.Memory, System.Buffers, System.Numerics.Vectors,
System.Threading.Tasks.Extensions) reference each other, and in a player those names resolve
against Unity's own netstandard2.1 profile, not against the excluded plugin copies -- the same
fact `tools/build-libs.ps1` records from the other direction in its $unityProvided block.
Telling a real break from a backfilled shim needs the Editor's playback-engine assembly set,
which CI does not have. That gate would have blocked every PR on its first day and been deleted
by the first person it inconvenienced. The shipped one answers a narrower question truthfully
instead, and its header says which question it declines.
