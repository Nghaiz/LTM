The Unity client's default playerId no longer collides with the load harness's first client.

FOUND BY A RUN, NOT BY READING. The first two-client harness run after #151 landed lost a
client. The Editor's own NetClientBootstrap and harness client 0 both claimed playerId 1 --
GameClientConfig defaulted to 1, and JoinTicketSource.Mint numbers synthetic clients from
clientIndex + 1 -- so the shipped default collided with the shipped harness by construction:

    [net] join ticket signed for player 1 as 'player'
    [net] join admitted for player 1
    [net] conn 1 joined as actor 41
    [net] join rejected: AlreadyConnected          <-- harness client 0
    [net] join admitted for player 2               <-- harness client 1

Lane B runs THREE rendered clients (two observers plus a driver, for phase-3-harness.md check
7). All three would have claimed 1 together, two would have been refused, and the refusal is
reported to the client as a bare InvalidTicket -- which reads as a full server.

MEASURED IN THE LIVE EDITOR after the fix, against the shipped GameClientConfig:

    [proof] default PlayerId = 29245  (reserved ceiling 1024)
    [proof] above harness range = True  nonZero = True
    [proof] stable within the process = True
    [proof] env override wins = True (got 7)

29245 is the Unity Editor process's own id. Three facts matter and each is asserted above:
above the reserved ceiling, so it can never land in the harness's range; stable within a
process, so a reconnect inside one session is not silently a different player; and still
overridable, because a run that has to be replayed against fixed identities needs to say so.

WHY PROCESS ID AND NOT A CONSTANT. Any constant collides with something. The previous one
collided with the first client of the harness that ships in this repository. A process id is
the cheapest thing that differs between two instances on one machine, which is exactly the
configuration lane B is.

THE TRADE, STATED. The id differs between runs, so a report naming it is not reproducible by
re-running. That is acceptable because the id is not an input to anything simulated -- no seed,
no spawn position, no network behaviour depends on it -- and because BuildJoinTicket logs the
id it minted with, so the report can record what actually happened. Set
IRONFRONT_CLIENT_PLAYER_ID explicitly when identities must be fixed.

.env ON THIS MACHINE deliberately leaves IRONFRONT_CLIENT_PLAYER_ID BLANK. Pinning a value
there would be worse than the default: lane B's three clients all read the same .env and would
all claim it. The runner sets it per instance.

A SECOND DEFECT, FROM THE SAME RUN. The harness's connect-failure hint asserted one cause --
"the server has a shared secret and this ticket was not signed with it" -- for DisconnectReason
.InvalidTicket, which the server returns for any of six TicketRejection values and deliberately
does not disambiguate (a handshake that says which check failed is an oracle for forging a
ticket one byte at a time). The real cause that day was AlreadyConnected, and the message sent
the reader hunting a signing problem that did not exist. It now names the generic-by-design
reason, points at the server log for the specific one, and lists the two this harness actually
hits.
