## 2. The plan was stale in one material way, and it mattered

**Task 2a's premise was wrong.** The plan states that `ServerMessageType.PlayerList = 0x4B`
is "declared **and nothing else exists** — zero message struct, zero router case". That was
true when the debt-closure track was drafted and false by the time it ran: **V3 (#135) had
already shipped the struct, the codec, the router case, the `OnPlayerList` event and spec
§ 4.11.** The debt ledger caught this and graded C-3 as `VERIFIED-OPEN (**two of three
sub-parts already closed**)` — Phase 0's per-row re-verification doing exactly the job it
was bought for.

What was genuinely open was the **sender**: `ServerEventWriter.WritePlayerList` had zero
callers anywhere in the repository, four phases after it was written. So task 2a became
"give the writer a caller and the event a subscriber", not "build the message".

**The consequence for scope.** Because the codec already shipped, P-D8's `PROTOCOL_VERSION`
question is moot — no byte moved. Acceptance criterion 2 is met and asserted
(`PlayerListVersionPinTests`), and that criterion turned out to *decide* a design fork; see
§ 4.

## 3. The asymmetry that let a writer sit uncalled for four phases

`ClientWiringGate` has failed the build since V10 whenever a `ClientMessageRouter` event
loses its last subscriber. It had **nothing equivalent for the server**, because the tool
only ever inspected router events. So:

- the **client** half of `S_PLAYER_LIST` was reported as a KNOWN GAP on every single CI run;
- the **server** half — a writer nothing called — was reported by nothing at all.

One direction was watched and the other was not, and the unwatched one is where the message
actually stops existing. **G6** (`WriterCoverageRunner`) closes it: every
`ServerEventWriter.Write*` method, read off the type by reflection, must be named by an
invocation in production code.

Two details worth carrying:

- **It scans wider than the source half.** Two writers are called from the library
  (`ServerVehicleLifecycleSink` sends `S_VEHICLE_SPAWN` / `S_VEHICLE_DESPAWN`), so a scan
  limited to `Assets/Scripts` would report both dead. It is deliberately *not* merged into
  `DefaultRoots`, which would run every per-file client rule over the library.
- **It ships with an empty exemption list**, which on its own is indistinguishable from a
  rule that cannot fire. `WriterCoverageGateTests` is what distinguishes them — the red path
  is exercised against a fixture where the call is absent, on every run.

`KnownUnwiredEvents` is now **empty again**. V3's `OnPlayerList` entry named its own
retirement condition ("the client-flow phase that also adopts `ClientCombatState` and
`ScoreUi`") and this was that phase, so it retired on SUBSCRIPTION rather than sitting
stale-but-green the way `OnCapturePoint`'s predecessor did.

## 4. The names are not usernames, and the plan's own criteria decided that

Task 2a needed a name source. There isn't one: **the game server never parses a
`JoinTicket`.** `OnClientConnected` receives a `ConnectionInfo` and nothing else; the
ticket's `displayName` field is written by the master server and read by nobody on this
side.

Plumbing the real username through needs a new client→server message carrying the ticket.
**Acceptance criterion 2 forbids that** — a new opcode moves `PROTOCOL_VERSION`, which the
criterion pins. Verifying the ticket would additionally require the master's shared secret
on every game server, which is a deployment decision and not a debt repayment.

So the table carries `#<playerId>` from the transport, falling back to `Player <actorId>`.
A killfeed that reads `#1042 → Player 3` is a worse name than the username and a strictly
better one than the bare actor id it rendered before — and the wire, the writer, the router
and the table are all in place for the real name the moment a join handshake carries one.
This is stated on `ServerPlayer.DisplayName` rather than left for someone to discover.

## 5. Two decisions that three phases had passed along

Both were handed forward and dropped. Phase 2 takes them.

**C-10 — a wreck damages.** V1-D5 handed "should `Vehicle.Explode()` do blast damage" to V4
as a gameplay decision; V4 did not take it, and `ExplosionKind.Vehicle` shipped with zero
producers. `Vehicle.Explode()` now calls `ActorManager.Explode(..., ExplosionKind.Vehicle)`.

> **Balance note, as the plan required.** Taking cover behind a burning vehicle is now
> dangerous. That is the intended consequence, not a side effect.

**C-11 — `ExplosionKind.Environment` gets a source.** V1 → V7, same shape, same outcome: the
member existed, the client's effect table indexed it, and nothing could ever emit it. The new
`ExplosiveProp` (fuel drum, gas cylinder) emits it through the same server-authoritative
path as every other blast. **Honest limit:** placing drums in a map is content work and no
scene carries one yet — the component is wired to its *callers* (a bullet sets one off; a
blast chains into neighbours), not to a level.

### A latent bug the wreck blast forced into the open

`ActorManager.Explode`'s vehicle loop index-walked the **live** `instance.vehicles` list,
above a comment asserting that nothing removes from it during the loop. That assertion was
already false — `vehicle.Damage(...)` → `Die()` → `ActorManager.DropVehicle` removes the
entry mid-iteration, and an index-walked `List` that shrinks under you **skips the next
element**. A wreck detonating inside a cluster of vehicles is what makes it routine rather
than occasional. The loop now iterates a reused snapshot.

The same comment also warned that a future chain-detonation would silently corrupt the
shared victim buffer. It does not: `Die()` reaches `Explode` through `Invoke(..., 0.3f)`, so
a chain is **sequential rather than nested** and the buffer is never re-entered. The
warning was right to exist and the hazard it named is genuinely not present — recorded here
because "we checked and it is fine" is only useful if the check is written down.

## 6. Task 2e — a prepared patch, and why the library test alone proves nothing

`AuthoritativeFlight` has shipped default-off since V7 behind a remark saying that turning it
on without first deleting the engine-side damage call would run both simulations and apply
damage twice. **That remark was the entire safety mechanism**, and the flag was a bare
settable auto-property with zero assignments anywhere.

The patch is now written and the flag is still off:

- `ProjectileDamageOwnership` (library) resolves the single owner from role + flag.
  Offline ignores the flag entirely — single-player has no stepper, so a build that read the
  flag as "the library owns this" would silently stop doing damage.
- `NetProjectileAuthority` (Unity) is the role adapter; `ServerProjectileBridge` pushes the
  flag to it on assignment.
- All three engine damage sites consult it.

**`ProjectileDamageOwnershipTests` proves the partition and nothing more.** It cannot see
whether `Assembly-CSharp` actually asks — no netstandard assembly references it. A suite that
was green while all three call sites were unguarded would be exactly the shape of
`green-that-proves-nothing`. So the other half is **G7**, a gate rule that fails the build if
any of the three loses its guard. It was **observed RED against all three sites** before the
patch, which is the recorded red proof.

G7 needed two corrections during authoring, both worth carrying:

1. **It over-matched at first.** `Explode` is also the name of the two overridable wrappers
   that *contain* the damage call, so an unqualified match reported `ExplodingProjectile.cs:57`
   and `GrenadeProjectile.cs:78` — call sites that apply no damage and would have had to be
   guarded twice or exempted. The receiver is now pinned to `ActorManager`, with a fixture
   proving it stayed pinned.
2. **It accepts two guard names, deliberately.** The `ActorManager.Explode` sites ask
   `LibraryOwnsProjectileDamage` ("is somebody else about to?"), *not*
   `!EngineAppliesProjectileDamage` — because that same call also applies the corpse ragdoll
   impulse a client must keep (AD-4). Accepting only the stricter name would have forced
   those two sites to switch off every client's corpses in order to satisfy a gate.

## 9. Three Unity compile traps, recorded because they recur

Full detail in [the compile proof](2026-08-19-phase-2-unity-compile.txt). Briefly:

1. **`dotnet build` passing says nothing about Unity.** Unity reads the **prebuilt DLLs** in
   `Assets/Plugins`, so a new library type is invisible to `Assembly-CSharp` until
   `tools/build-libs.ps1` runs. `ProjectileDamageOwnership` hit this.
2. **`Assembly-CSharp` declares its own `Action`** — a countdown timer (see
   `ScoreUi.bluePulse`) — which shadows `System.Action`. `using System;` does not win, and
   the symptom is `CS0066: event must be of a delegate type`. Every event in
   `MatchScoreboard` is fully qualified with a comment saying why.
3. The payload constant is `MAX_PAYLOAD`, not `MTU_SAFE_PAYLOAD`.

### Criterion 3, stated precisely

**Nothing in the repository rendered the killfeed at all.** `KillfeedModel` shipped in
phase-02, is exercised by tests, and had zero consumers — so "the killfeed showed an actor
id" was itself generous; it showed nothing. A real HUD element belongs on
`Ingame UI Container.prefab`, and **§ 8 of the plan forbids Phase 2 from touching prefabs or
scenes**. So the killfeed and the death screen are drawn with **IMGUI from components that
already sit on the `NetClient` object**, marked as stopgaps in their own remarks. The state
behind them is the shipped library model, so replacing the drawing touches none of it.

A **Play Mode observation** that a line renders with a name is not claimed here. Two rendered
clients are Phase 3's harness, and this phase's evidence is a compile plus the gates.
