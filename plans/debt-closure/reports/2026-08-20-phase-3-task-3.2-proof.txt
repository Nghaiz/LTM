The open defect, and the four hypotheses already falsified
------------------------------------------------------------------------------

SYMPTOM. Both clients are denied. The client reports ServerFull; the server
logs '[net] join rejected: BadSignature'. Those are different reasons for the
same handshake, and only one of them can be right.

The server is healthy at the moment it denies. Read live by reflection, mid-run:

  isPlaying=True
  loop=present
  tick=153 conns=0
  freeIds=16
  boundPort=27017

  and during an in-flight run:
  tick=209
  type=UdpTransportServer ConnectionCount=0
  _freeIds.Count=16
  _connectionCount=0
  _maxConnections=16
  _byId.Length=17
  _byEndpoint.Count=0
  _accepted.Count=0
  _playerIdToConnection.Count=0

CORRECTED 2026-08-20 (phase 3B). The paragraph that stood here read:

  'ConnectDenyReason.ServerFull is sent from exactly one place —
   UdpTransportServer.cs:265 — ... Both readings cannot be true of one server.'

That premise is false, and it is what sent this investigation down to the
transport layer and kept it there. A ServerFull the client can observe has TWO
senders:

  UdpTransportServer.cs:265        ConnectDenyReason.ServerFull — denied DURING
                                   the handshake, when
                                   '_connectionCount >= _maxConnections ||
                                    _freeIds.Count == 0'
  ServerTickLoop.cs:1275           DisconnectReason.ServerFull — disconnected
                                   AFTER the handshake already succeeded,
                                   when OnClientConnected cannot claim a
                                   player slot

The second reaches the client verbatim: Connection.cs:400 puts the reason byte
on the wire, Connection.cs:212 reads it back. MapDeniedReason is not involved.

So the two readings the paragraph called mutually exclusive are not
simultaneous — they are sequential. '_freeIds=16, _connectionCount=0' is the
state AFTER an accept and a same-tick disconnect. The server was never full;
it admitted the connection and then threw it out one layer higher up, because
exactly one prefab in the scene carried '_availableForPlayers = 1'. That is the
phase-3A defect, fixed in #154 by ServerPlayerSlotPool.

FALSIFIED, each by a test rather than by argument:

  1. Stale plugin DLL          — ticket bytes are identical across both builds
  2. Mismatched shared secret  — same length and same SHA-256 prefix on both sides
  3. Leaked slots on a reused  — a virgin port (27017) on a freshly started server
     port                        with 16 free ids denies identically
  4. Leaked sockets across     — after the run only 27017 is bound; 27015 and 27016
     Play Mode sessions          were released. Nothing survives a session

WHY 1-4 COULD NOT HAVE REACHED IT (added 2026-08-20, phase 3B). All four are
transport-layer hypotheses, and each was correctly falsified. The defect was one
layer above the transport, in the Unity application: the handshake SUCCEEDED and
ServerTickLoop.OnClientConnected then disconnected the connection for want of a
player slot. No test aimed at the transport could have seen it, however well
that test was run. The reasoning was sound; the altitude was wrong.

  5. RESOLVED — there were THREE participants, not two

     'SYMPTOM' above treats ServerFull and BadSignature as two accounts of one
     handshake, of which one must be wrong. Neither was wrong. --smoke runs two
     clients, and the Editor play session runs a THIRD — its own local
     NetClientBootstrap, which the report never accounted for:

       ServerFull    the two harness clients, post-handshake, phase-3A's
                     one-player-slot defect (fixed in #154)
       BadSignature  the Editor's own local client, at handshake time,
                     presenting PendingJoin.CreateUnsignedTicket() —
                     64 zero bytes (PendingJoin.cs:78, NetClientBootstrap.cs:180)

     Measured inside the live server process against its own configured secret,
     phase 3B:

       unsignedTicket len=64 allZero=True
       JoinTicket.Verify(unsigned) = BadSignature
       JoinTicket.Verify(signed)   = Valid
       server acceptUnsignedTickets=True   (inert: a secret is set)
       local NetClientBootstrap in play session = True
       OnValidateTicket subscribers = 1

     JoinTicket.Verify returns BadSignature from exactly one branch — an HMAC
     mismatch — so a zero ticket can produce nothing else. The client is told
     the generic InvalidTicket (NetServerBootstrap.cs:373 logs the specific
     reason server-side and deliberately does not send it), which is the
     '[net] disconnected: InvalidTicket' line that follows every BadSignature in
     the Editor log.

     No packet capture was needed. The suggestion to reach for one followed from
     the false premise corrected above.
