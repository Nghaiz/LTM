------------------------------------------------------------------------------
What the harness DID prove about itself
------------------------------------------------------------------------------

The bring-up is not a mystery at every layer — three of four are demonstrated:

  * real UDP round trip      the server answers; every failure below is a
                             CONNECT_DENIED that travelled the wire, not a timeout
  * ticket minting works     run 1 used the unsigned 64-zero-byte ticket and was
                             refused InvalidTicket; JoinTicketSource was added, and
                             the refusal reason CHANGED. The server stopped saying
                             the signature was absent
  * the codec is not stale   JoinTicket.Issue over identical inputs produces
                             byte-identical tickets from the source build and from
                             Assets/Plugins/Ironfront.Net.Protocol.dll, and the
                             secret is identical on both sides (len 44, sha256-8
                             3E7926DF76B511E8 measured in the Editor AND in the harness)

------------------------------------------------------------------------------
The open defect, and the four hypotheses already falsified
------------------------------------------------------------------------------

SYMPTOM. Both clients are denied. The client reports ServerFull; the server
logs '[net] join rejected: BadSignature'. Those are different reasons for the
same handshake, and only one of them can be right.

The server is healthy at the moment it denies. Read live by reflection, mid-run:

  isPlaying=True
  loop=present
  tick=153 conns=0
  freeIds=16
  boundPort=27017

  and during an in-flight run:
  tick=209
  type=UdpTransportServer ConnectionCount=0
  _freeIds.Count=16
  _connectionCount=0
  _maxConnections=16
  _byId.Length=17
  _byEndpoint.Count=0
  _accepted.Count=0
  _playerIdToConnection.Count=0

ConnectDenyReason.ServerFull is sent from exactly one place —
UdpTransportServer.cs:265 — and only when
'_connectionCount >= _maxConnections || _freeIds.Count == 0'. The probe above
shows _freeIds at 16 and _connectionCount at 0 on the very server that is bound
to the port under test. Both readings cannot be true of one server.

FALSIFIED, each by a test rather than by argument:

  1. Stale plugin DLL          — ticket bytes are identical across both builds
  2. Mismatched shared secret  — same length and same SHA-256 prefix on both sides
  3. Leaked slots on a reused  — a virgin port (27017) on a freshly started server
     port                        with 16 free ids denies identically
  4. Leaked sockets across     — after the run only 27017 is bound; 27015 and 27016
     Play Mode sessions          were released. Nothing survives a session

STILL OPEN. Something other than ServerTickLoop.Current.Transport answers on the
port, or the deny reason is not the one the server believes it sent. Separating
those needs packet-level capture (the transport already ships PacketLogger), not
more reasoning.

OWNERSHIP. Phase 3 section 7: 'If a check fails because of a defect, the defect is
filed and fixed in its own commit — never patched inside the harness.' No
workaround was added to the harness, and the smoke gate was not lowered to make
this run pass.
