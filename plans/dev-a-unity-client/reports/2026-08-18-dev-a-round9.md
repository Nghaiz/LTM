### 4. `ServerActorRegistry` splits into two instances — **reproduced 3× from cold starts**

`ServerCombatBridge._registry` and `ServerActorDamageSink._registry` hold a *different*
`ServerActorRegistry` than the one every actor registers into.

```
run 1 : bridge/_registry count 0 hash -146604542 | Instance count 41 hash 360395118 | ReferenceEquals False
run 2 : live registry 41 actors | _combat: 0 -> repointed | _damageSink: 0 -> repointed
run 3 : live registry 41 actors | _combat: 0 -> repointed | _damageSink: 0 -> repointed
```

The ordering: `ServerTickLoop` reads `ServerActorRegistry.Instance` during play-mode scene
deserialisation → `ResetOnLoad()` at `ServerActorRegistry.cs:201`
(`[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]`) nulls `_instance` → actors register from
`OnEnable`, later still, into a fresh second instance.

**`BuildTargets` therefore scans a registry with 0 actors and the candidate span handed to
`LagCompensator` is empty on every shot.** Measured over ~31 000 ticks before the repoint:
`ShotsResolved 507, ShotsHit 0, ShotsOccluded 0, kills 0, DeathsReported 0, hitConfirms 0`. No
bullet in the game can hit anything.

`enterPlayModeOptionsEnabled = False`, so this is not a domain-reload shortcut artefact. It is
deterministic, and it is the highest-severity item in this report.

### 5. The authoritative `MoveState` free-falls

`MovementCore.Step` takes `IsGrounded` as an input. `ServerPlayer` falls back to `MoveDetached`
when `Actor.Movement == null`, and **`NetMovementAgent` is on no prefab and in no scene** — so
`Actor.Movement` is null for every session.

```
session 9  statePos y = -11218    transform y ~ 25
session 11 statePos y =  -4225    transform y ~ 25
Player Fps Actor(Clone)  y = -120941
```

The visible actor stands on the ground while the authority the server reconciles against is 11 km
below it. `SpeedViolations: 735` was entirely this. Holding the authoritative state on the
transform for the duration of a run takes it to **0**, which is what every E-row reading below is
taken under.

### 6. `AiActorController.Die` NRE at `AiActorController.cs:1894`

Pre-existing, fires on bot death. Operationally significant for a different reason — see §5.

### 7. **NEW: a match reset empties the actor-id pool while 41 actors still hold their ids**

`ServerStateAudit.ResetForNewMatch()` calls `_ids.ResetAll()`, which clears `_inUse` and re-enqueues
the whole id space as free. The 41 actors holding those ids are untouched.

```
mid-round        : ids in-use=41 free=23 quarantined=0 | registry 41
after auto-reset : ids in-use=0  free=64 quarantined=0 | registry 41
```

The scene's match cycles on its own (`Playing → Ended → Resetting → WaitingForPlayers → Warmup`),
so this is reached in ordinary play, not only by an explicit reset. Two consequences:

- **`ActorIdsInUse` reads 0 while 41 ids are in use.** The audit's leak check is structurally blind
  after the first round — the same shape of "the counter could not have detected anything" you
  documented in `ServerActorRegistry.UseIdPool`'s remarks, one layer up.
- **`_free` offers ids 1..41 again.** The next `TryAcquire` can hand out an id a live actor already
  holds, which is exactly the duplicate-id state `Register`'s guard and the quarantine exist to
  prevent.

Emptying the *quarantine* on reset is deliberate and fine — `ServerStateAudit.cs:38-42` says so
explicitly. Clearing `_inUse` is the defect: those ids are still in use.

Suggested fix, yours to take or leave: have `ResetAll` re-mark as in-use every id currently held by
a registered actor, or have `ResetForNewMatch` re-acquire from the live registry after the reset.

## 3. S5 / A9 — bot LOD

**You asked for:** 32-bot tick p99 with `AlwaysOn`, with `Scheduler`, plus the AI cost in both.

**Server tick p99 is flat across all three arms.**

| Arm | server tick p99 | AI ms/frame mean | AI p99 | all script Update p99 |
|---|---|---|---|---|
| `Scheduler` (shipping) | **4.830 ms** | 1.178 | 5.354 | 15.715 |
| `AlwaysOn` (LOD off) | **4.694 ms** | 1.354 | 4.730 | 17.166 |
| `AlwaysOff` (floor) | 4.602 ms | 0.404 | 1.357 | 8.103 |

40 bots (the scene has 40, not 32 — slightly heavier than the row asks for), 480 samples per arm,
`granted=14370 skipped=9030` → **38.6 % of bot-ticks skipped**.

That flatness is structural, not a null result: `AiActorController` runs in `Update`, and
`ServerTickLoop`'s stages do not contain it. **No LOD setting can move tick p99, because the AI is
not in the tick.** The row as written cannot distinguish the two modes; what does distinguish them
is the AI's own cost in the same frame budget.

**AI cost above the `AlwaysOff` floor:** `AlwaysOn 0.951` ms/frame, `Scheduler 0.775` ms/frame — a
**18.5 % saving while skipping 38.6 % of ticks**.

The gap between 18.5 % and 38.6 % is the finding. A skipped coroutine does
`yield return null; continue;`, so a gated-off bot re-polls **every frame**, while a working bot
sleeps on `WaitForSeconds(0.2..1.0)`. The marker call counts show it directly: **326 AI marker calls
per frame with everything skipped, against 103 with everything working** — a skipped bot is entered
three times as often as a busy one. `AlwaysOff` costing 0.404 ms/frame while doing no AI work at all
is that polling, and it is the floor the saving has to be measured against.

Your comment at the guard says the `yield return null` buys re-entry on the frame the bot returns to
interest instead of up to a `WaitForSeconds` later. That is a real property and I am not arguing
against it — but the price is that the gate eats roughly half of what it saves. Worth comparing
against a `WaitForSeconds(0.1f)` on the skip path before this is called done.

**Two methodology notes, because the first run of this got it wrong.**

- `Recorder.Get` returns `isValid == true` for a sampler that does not exist — it creates one. My
  first pass recorded `"AiActorController.Update()"`, read 0.000 ms for 900 frames in both arms, and
  the `isValid` check said nothing was wrong. The real markers are deep-profile mangled:
  `Assembly-CSharp.dll!::AiActorController.AiScan() [Coroutine: MoveNext] [Invoke]`. Eight of your
  nine `AiWorkAllowed` guards are in coroutines, whose time is **not** in `BehaviourUpdate`, so a
  single recorder on that marker measures one ninth of the workload. The figures above sum all nine.
- Running the arms back to back reported `Scheduler` as the *slower* arm. Editor settling and cold
  A* caches loaded onto whichever arm ran first. The figures above interleave three arms in blocks
  (8 settle + 32 sampled frames, 15 rounds).

**Environment caveat, and it is a real limit on these numbers.** The Editor was unfocused at
**~8 fps** (measured: 112 frames in 13.6 s), where the tick scheduler is catching up and dropping
ticks — `DroppedTicks += 597` within a single arm. Every arm ran interleaved under identical
conditions, so the *comparison* holds. The absolute milliseconds do not represent a headless Linux
server and should be re-taken on the D1.2 build once it exists.

Both AI prefabs are back to `_mode: 0` (`Scheduler`) on disk; only the runtime property was
scripted, and the probe restores all 40 gates in its `finally`.

## 4. D1.2 — the build is now the last thing standing, and three real bugs came out of it

Round 8 filed this as "blocked on the project lock". It is not blocked on that any more: the build
runs. `tools/build-server.ps1` launches a second Unity on `Ironfront_Reborn/` and two Editors cannot
open one project, so instead of closing the Editor I drove `Ironfront.EditorBuild
.BuildDedicatedServer` **inside** the Editor that already holds the lock, in three steps through MCP
— switch target, build, restore (`tools/probe-build-switch.cs`, `-run.cs`, `-restore.cs`). That got
far enough to find three defects, two of them in our code, all three fixed.

**1. The MCP package makes every player build fail with 1284 compiler errors.** Its dependency
resolver writes `UNITY_MCP_READY` into *every* platform's `scriptingDefineSymbols`, Server included.
`com.IvanMurzak.Unity.MCP.Runtime.asmdef` gates on that define and declares `includePlatforms: []`,
so it compiles into the player — while every DLL in its `precompiledReferences` (`McpPlugin.dll`,
`ReflectorNet.dll`, `R3.dll`, `Microsoft.Extensions.*`, SignalR) carries
`defineConstraints: [UNITY_EDITOR]` in its own `.meta` and is therefore absent. 429 errors across
1284 log lines, none of them ours. The asmdef lives in `Library/PackageCache` and is regenerated on
every resolve, so it cannot be fixed there; and the define cannot simply be deleted, because the
Editor compiles with the active platform's set and the MCP integration is wanted in the Editor.
`EditorBuild.cs` now strips it from the Server define set for the duration of the build.

That also settles the shipping question round 8 left open: with the define gone the MCP assembly is
excluded outright, so the plugin and its NuGet closure — SignalR, `Microsoft.Extensions.*`, and the
Roslyn `Microsoft.CodeAnalysis.dll` — **cannot** reach the server image. An editor automation bridge
that speaks HTTP and compiles arbitrary C# has no business in a public game server.

**2. `EditorBuild.cs` reported a 49 MB success for an empty directory.** With the compile fixed the
build logged `[build] dedicated server complete -> …\build\server\Ironfront.Server.x86_64
(49323444 bytes, 86 warning(s))`, zero errors — and `build/server` was empty, with no
`Ironfront.Server*` anywhere on the disk. `BuildPipeline.BuildPlayer` returned
`BuildResult.Succeeded` while, from inside the same call:

```
UnityException: Build target 'StandaloneLinux64' not supported
  at UnityEditor.PostprocessBuildPlayer.Postprocess (…)
```

Postprocess is the step that installs the compiled player into the output directory. It took 166 ms.
So the player compiled, was never written, and the pipeline called that success — and our
`summary.result != BuildResult.Succeeded` check was blind to it. `EditorBuild.cs` now verifies the
output tree (executable plus a `*_Data` folder beside it) before declaring success. A post-condition
on the output rather than a pre-flight on the target, deliberately: an output directory with no
player in it is the one symptom every silent-write failure shares. Without it a batch run exits zero
and the packaging step tars up an empty directory, which then fails in the container an hour later as
something else entirely.

**3. A batch build would have committed a broken `ProjectSettings.asset`.** Two compounding bugs
found while cleaning up after the above. `EditorApplication.Exit` terminates the process without
unwinding the managed stack, so the `Exit(0)` on the old success path — and the `Exit(1)` inside
`Fail` — skipped the `finally` that restores the stripped define. And separately, `BuildPlayer`
flushes the project settings itself partway through the build, so the stripped set reaches
`ProjectSettings.asset`, a *committed* file, and an in-memory restore leaves the file dirty and
wrong. Observed directly: `git diff` showed `Server:` with no defines after a build whose restore had
demonstrably run. `EditorBuild.cs` now has a single exit, placed after the `finally` and outside the
`try`, and `RestoreDefines` calls `AssetDatabase.SaveAssets()`.

### What the module actually needed, and the one thing I cannot do from here

"Not supported" in defect 2 does not mean the module is missing. It means the build *post-processor*
was not found, and that comes from the registry of platform support modules the Editor loaded **at
startup** — not from the filesystem. `tools/probe-build-modules.cs` reads that registry:

```
platform extension assemblies in this domain (1): UnityEditor.WindowsStandalone.Extensions
  StandaloneLinux64    supported(disk+licence)=True  moduleLoaded=False  postProcessor=NULL
  StandaloneWindows64  supported(disk+licence)=True  moduleLoaded=True   postProcessor=WinPlayerPostProcessor
  LinuxStandaloneSupport created=2026-08-17 22:25:16
  this Editor started    =2026-08-17 21:40:03
```

The module was installed 45 minutes after the Editor started. `BuildPipeline
.IsBuildTargetSupported` answers from the installed files and the licence, which is why it said
`True`, and `SwitchActiveBuildTarget` succeeded for the same reason — the two states are
indistinguishable through any public API, which is exactly what made the failure silent.
`ModuleManager.RegisterPlatformSupportModules()` is guarded ("already registered, not loading"), so
there is no in-session recovery. **The Editor has to restart.** Nothing in the project is wrong.

The required variation does exist: the Server target is `Mono2x` with `development=False`, so the
build wants `Variations/linux64_server_nondevelopment_mono`, and that ships in the installed module.

So what remains:

No tag and no digest again — but the reason has moved from "the build has never run" to "the build

## 5. Two operational traps that cost real time

Not checklist items. Both are the kind of thing that reads as a netcode failure and is not, and the
next person to open this project will hit them.

**Console Error Pause silently prevents play mode from ever initialising.** It was on. Play mode
paused on the pre-existing `AiActorController.Die` NRE (defect 6) before the server finished coming
up, and the symptom is `isPlaying=True`, `frameCount=3`, no `ServerTickLoop`, no actors, no
`ActorManager` — indistinguishable from the netcode failing to bind. The server tick sat frozen at
4811 and the synthetic client timed out. Cleared with
`UnityEditor.LogEntries.SetConsoleFlag(4, false)`, after which the server came up on the next start
(`CurrentTick=246`, 41 actors, `ActorManager.instance=ok`).

**A script recompile while in play mode reloads the domain and kills the server permanently.**
Statics reset — `ServerTickLoop.ResetCurrentOnLoad`, `ServerActorRegistry.ResetOnLoad` — while
MonoBehaviours survive, so `Awake`/`Bind` never re-run and `ServerTickLoop.Current` stays null for
the rest of the session. It does not throw and it does not log. Any edit under `Assets/Editor` needs
a deliberate stop/start of play mode, which is why every probe in this round was batched into one
file.

Minor, for whoever hits it: `console-clear-logs` fails because
`Temp/mcp-server/ai-editor-logs.txt` is held by another process, so `console-get-logs` serves a
stale cache. The game's own log under `AppData/LocalLow/SteelRaven7/Ravenfield/Logs/` is the
reliable source. And `DisconnectReason` is in `Ironfront.Net.Transport`, not `.Protocol`, with no
`ServerShutdown` member.
